# 0020 同步格式 v2：仅本机边界与歌词绑定字段

- 状态：已接受
- 日期：2026-11-10
- 关联：ADR-0016（git 同步）、ADR-0018（本地音乐库）、ADR-0019（歌词绑定）
- 设计：[sync-design.md](../sync-design.md)

## 背景

v0.7.0 往同步仓库里加了两类信息：

1. `playlists.sync_excluded`：文件夹歌单与仅本机歌单不进仓库，导入也不能删；
2. `annotations/*.json` 的新字段 `lyric_bind`：可跨设备复现的歌词绑定。

旧客户端不认识这两样。它会把仅本机歌单当成普通歌单重新导出，或者在
`KeepLocal=false` 导入时把它们删掉；注释里的未知字段也会在重新导出时丢失。
同步边界涉及**数据删除**，不能靠「旧客户端忽略未知字段」赌安全。

## 决策

- `MetaVersion` 从 1 升到 2；`meta.json` 不新增字段，保证旧客户端读到的是
  「版本不匹配」而不是「JSON 损坏」。
- 新客户端 `DecodeMeta` 接受 v1 与 v2：
  - v1 仓库正常同步，首次成功同步后写回 v2 `meta.json`，
    同步页提示「仓库已升级到 v2，旧版本客户端将无法同步」；
  - v2 正常同步；
  - 高于 v2 报 `ErrSchema`，不尝试降级。
- 升级不可回退：不允许把 v2 写回 v1。
- 多设备用户必须先升级所有设备，再让任意一台执行同步。

### 导出与删除共用同一份「可同步集合」

`ListPlaylistSnapshots` 增加 `WHERE sync_excluded = 0`，导出与
`ImportSnapshot` 的删除遍历共用它；`ListSyncAnnotations` 同时供导出与
`deleteMissingAnnotations` 使用，跳过本地曲目注释。单侧过滤一律视为 bug。

`BuildSnapshot` 另加两道防御：

- 会同步的歌单里混入 `source=local` 曲目 → 直接报错，不静默过滤；
- `sync_excluded=0` 的混合歌单引用 folder → 直接报错，不静默导出断引用。

导入时 `kind=folder` 一律按无效处理（`CreateFolderPlaylist` 之外的路径不存在
`root_path`，不能凭空造占位）。

## 理由

- 版本号是唯一的兼容性信号；写进 JSON 的字段顺序/未知字段都不能阻止旧客户端
  重新导出并丢数据。
- 升级发生在成功同步之后，失败的一轮不会留下半个 v2 仓库。
- 共用查询把「一侧改过滤」这类回归变成结构上不可能。

## 后果

- v1 与 v2 客户端不能长期混用；发布说明与同步页都要提示先升级。
- 元数据升级不重新派生密钥，其它设备只是格式变更，不需要重新输口令。
- 冲突处理沿用「同一实体两端都改才冲突」；绑定与 offset 在同一注释文件里，
  一端改绑定、一端改 offset 会整版冲突。

## 替代方案

| 方案 | 不采用的原因 |
| --- | --- |
| 只升 `meta.json` 不加版本号 | 旧客户端会当成损坏仓库或直接忽略 |
| 继续用 v1，靠字段可选兼容 | 旧客户端会删掉仅本机歌单，代价是用户数据 |
| 每个字段单独协商能力位 | 仓库层没有协商通道，且删除语义无法回滚 |

# ADR-0008 首版音频用 ffmpeg 外部解码，而不是纯 Go

- 状态：已接受（取代 ADR-0003 的首版方案）
- 日期：2026-10-20

## 背景

B 站音轨的编码矩阵很宽：`mp4a.40.2`（AAC-LC，192k）、`mp4a.40.5`（HE-AAC，64k，纯 Go 解码器普遍不支持）、FLAC（大会员）、`ec-3`（杜比）。
ADR-0003 的计划是 native + mpv 双后端，但 native 依赖的 `go-aac` 建仓很新，且只覆盖 AAC-LC。

## 决策

首版只做 **ffmpeg 子进程**：`ffmpeg -headers "Referer: ..." -i URL -f s16le -ar 48000 -ac 2 pipe:1`，
stdout 包一层增益链后交给 oto 播放。

## 理由

1. 一次覆盖全部编码，不需要先做编码探测与降级矩阵。
2. 选轨策略可以保持简单：优先 `mp4a.40.2` 的最大带宽，天然避开 HE-AAC。
3. 可以在一天内验证"能出声、能 seek、能调音量"，把风险留给后面的优化，而不是一开始就赌解码器。
4. 实测：`BV1GJ411x7h7` 3 秒 PCM 字节数完全符合 48k×2×2×3，进度与总时长准确。

## 后果

- **ffmpeg 成为硬依赖**，README 必须写清。
- **seek 只能重启进程**（`-ss`），有 0.3–1 秒停顿，不是瞬时跳转。
- 解码错误只能通过 ffmpeg 的 stderr 文本呈现，粒度比进程内解码粗。
- 后续要"去 ffmpeg 化"时，按 ADR-0003 补 `Decoder` 接口即可，引擎与 UI 不受影响。

## 替代方案

- 纯 Go（`go-aac` + `go-m4a` + `oto`）：最终形态，但需要自写 fMP4 解封装与 seek 映射，首版风险过高。
- mpv 子进程 + JSON IPC：能力更强（缓存、软音量、无缝切歌），但引入更大的外部依赖，且本机不一定装了 mpv。

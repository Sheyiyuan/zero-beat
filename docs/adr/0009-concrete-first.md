# ADR-0009 先写具体实现，第二个音源出现时再抽 Source 接口

- 状态：已被 [ADR-0010](0010-multi-source.md) 取代（第二个音源已出现，接口恢复）
- 日期：2026-10-20

## 背景

骨架阶段建了 `internal/domain`（Track / TrackSource）、`internal/source`（Source 接口 + 能力位 + 注册表）、`internal/match`、`internal/resolve`，
但实际只有一个音源。写实现时发现：

- 只有一个实现时，接口的每个方法都只能靠想象定义，方法签名改三次还没有第二个实现来校验。
- `Track` + `TrackSource` 两层模型在没有跨源匹配之前，只是把一张表拆成两张再加一次 join。
- 空接口会诱使后来的人按错误的形状实现第二个音源。

## 决策

删除 `internal/domain`、`internal/source`、`internal/match`、`internal/resolve` 与 `internal/audio/decoder`，
首版只保留真实被调用的结构：`store.Song`、`audio.Stream`、`bili.Stream`。

## 理由

1. 抽象的成本是「每次改动都要同时改接口与实现」，收益是「第二个实现能直接插进来」。只有一个实现时只有成本。
2. 先把能听歌的闭环做出来，才能知道真正的差异点在哪（例如：B 站的多 P、收藏夹、字幕歌词，哪些是平台特性，哪些是通用概念）。
3. 删掉的代码在 git 历史里，随时可以捡回来。

## 后果

- 加网易云时必须先补 `source.Source`（登录、搜索、取流、歌词、远端歌单），估计 3–5 人日；这是必要开销，不是浪费。
- 在抽象补齐之前，UI 里不能出现「按平台判断」的逻辑——否则第二音源进来会变成分支地狱。
- 如果第二个音源迟迟不做，这份「具体实现」就是最终形态，也不需要背抽象的债。

## 替代方案

保留骨架期的接口，边写边改：会在没有第二个实现的情况下反复重构接口，把时间花在猜测上。

# 实例锁与生命周期

## 锁解决什么问题

同一个数据目录同时跑两个播放实例会出：

- 两路音频同时出声；
- 两个 MPRIS 播放器（Linux），系统面板控制错对象；
- 两个进程写同一个 SQLite 的 `queue`/`settings`，后写覆盖先写；
- 同步仓库被两个进程同时操作。

`zero-beat-core` 已经有 `instance`：Unix 用 `flock(LOCK_EX|LOCK_NB)`，Windows 用 `LockFileEx`（加在文件第 4096 字节之后，避免锁头导致读不到 PID），锁文件里写 PID 只用于提示。GUI 复用同一把锁。

## 为什么不能靠「读 PID 文件」当锁

「读文件看有没有 PID」不是锁，只是提示：

| 问题 | 说明 |
| --- | --- |
| TOCTOU | 两个进程同时读到「没有 PID」，同时启动 |
| 崩溃残留 | 进程被 `SIGKILL` 后 flock 自动释放，但文件里的 PID 还在；只读文件会误判 |
| PID 复用 | 旧 PID 被别的进程占用，导致误报「已在运行」 |
| 命名空间 | 容器/沙箱里 `/proc` 不可靠，跨平台也没有统一的进程存活判断 |
| 竞争写 | 没有内核仲裁，两个实例仍可能都完成启动 |

flock 由内核在进程退出（包括崩溃）时自动释放，这正是它适合单实例的原因。文件内容只用来显示「谁在运行」。

**正确做法**：GUI 的 Go 核心先复用 TUI 的 `config.DataDir()` 确定桌面目录（Linux 包括 `XDG_CONFIG_HOME`），在 `ZeroStart` 里调用 `instance.Acquire(dir)`，成功后才调用会建表和迁移的 `store.Open`，随后初始化服务与音频。拿到锁后写入自己的 PID；拿不到时返回结构化错误（含 PID），Flutter 显示「另一个 zero-beat 已在运行（PID x）」。不能先开库再补锁。

`ZeroStart` 在进程内也须串行化并拒绝重复初始化；初始化失败逆序清理已创建的服务/数据库，最后释放锁。`ZeroStop` 必须可重复调用，关闭资源前先停止接收新任务。

Windows 用同一个 `instance` 包的 `LockFileEx`（锁在文件第 4096 字节之后，避免锁头导致读不到 PID）。GUI 的 `zero-core.exe` sidecar 持有锁，Flutter 只是客户端；Flutter 退出时结束子进程，锁随之释放。

macOS 用 `flock`，路径 `~/Library/Application Support/zero-beat/instance.lock`，与 TUI 共用；关闭窗口隐藏到 Dock/菜单栏时锁继续持有。

如果将来出现非 Go 的客户端，也只需要用 FFI 调 `flock`（两个 syscall），不需要发明第二套锁协议。

## 桌面启动与二次启动

```
GUI 启动
  ├─ 能拿到 instance.lock → 正常启动
  └─ 拿不到
       ├─ 能连上 gui.sock → 发送 {"cmd":"show"}，自己退出
       └─ 连不上 → 显示「已在运行（PID x）」，退出
```

- `gui.sock` 是 GUI 自己的激活端点（与 TUI 的 `control.sock` 区分），由核心监听；macOS 同一路径；Windows 对应命名管道 `\\.\pipe\zero-beat-gui`；
- 第二个实例不允许打开数据库、不初始化音频；
- 激活命令只做「显示主窗口/取消迷你模式」，不做数据操作。

### Windows sidecar 生命周期

- Flutter 启动 `zero-core.exe`，用 Job Object（`KILL_ON_JOB_CLOSE`）绑定子进程，父进程崩溃时子进程一起结束，避免孤儿核心继续占锁或写数据；声音仍由 Flutter 侧输出；
- 正常退出：先走 RPC `app.quit` 持久化，再关闭子进程；超时则强制结束；
- 子进程异常退出：Flutter 显示错误并提供「重启核心」，不静默假装还在播放；
- 不用「读 PID 判断」来清理孤儿进程；Job Object 由内核保证。

## 桌面窗口生命周期

状态：

```
             ┌──────────── 显示主窗口 ◄────────────┐
             │                                    │
             ▼                                    │
   ┌──────────────┐   关窗（默认）   ┌──────────────┐
   │   normal     │ ───────────────► │    mini      │
   └──────────────┘                  └──────────────┘
             │ 最小化/托盘                │ 双击/菜单
             ▼                            │
   ┌──────────────┐ ◄────────────────────┘
   │    tray      │   托盘菜单「显示主窗口」
   └──────────────┘
             │ 托盘菜单「退出」
             ▼
          quit（释放锁）
```

规则：

- **Linux 关窗默认进迷你模式**（用户明确要求「窗口退出后可以小窗继续运行」）；
- **macOS 关窗默认隐藏到 Dock/菜单栏**（平台习惯），迷你模式从菜单栏开启；Cmd+Q 才退出；
- 设置项可改为「关窗进托盘/菜单栏」或「关窗即退出」；
- 只要有窗口、托盘或菜单栏存在，进程就活着，Go 核心与播放继续；
- 真正退出只从托盘菜单或应用菜单触发，退出前：
  1. `controller.Persist()` 保存队列与进度；
  2. 停止引擎、注销系统媒体（Linux MPRIS / macOS Now Playing / Windows SMTC）、关闭 RPC/socket；
  3. 释放 `instance.lock`。

### 迷你窗口

- 尺寸约 380×140，无边框、置顶、可拖动；
- 内容：封面、标题/艺人、进度条、上一首/播放暂停/下一首、关闭（回托盘/菜单栏）；
- 双击恢复主窗口；右键菜单：显示主窗口、隐藏到托盘/菜单栏、退出；
- 不抢占焦点；多显示器跟随鼠标所在屏；
- Wayland 下置顶/无边框能力受合成器限制，做降级（普通小窗）；macOS 正常支持置顶/无边框。

### 托盘 / 菜单栏

- 菜单：显示主窗口、迷你模式、播放/暂停、上一首、下一首、退出；
- Linux 使用 StatusNotifier/AppIndicator（`tray_manager` 依赖 libayatana-appindicator）；macOS 使用菜单栏图标；
- 托盘不可用时不能静默丢窗口：回退为「关窗最小化」，并在设置里提示；
- 图标随深浅色切换；播放状态用图标角标或 tooltip 表示。

### 最小化、休眠、锁屏

- 最小化/隐藏不暂停；
- 系统休眠：由 media_kit/系统处理；恢复后校准位置，不重复起播；
- 桌面锁屏不影响播放（与 TUI 一致）；
- 退出前若有正在进行的下载/同步，提示确认，不静默丢弃。

## Android 生命周期

- 没有 TUI，不使用桌面 `instance.lock`；Activity 与 audio_service 共用同一进程内的核心，重复启动/恢复不能再创建一套 Go 核心或 Player；
- 播放前启动 audio_service 前台服务，通知常驻；
- 用户从最近任务划掉 App：按系统策略，前台服务可能继续；不承诺「划掉后继续播放」，以通知的停止按钮为准；
- 进程被杀后重启：从 `queue` 表恢复队列与进度，不自动起播。

## 生命周期验收

- TUI/GUI 持锁时启动第二 GUI：不调用 `store.Open`，不迁移数据库、不初始化音频；激活失败也不进入初始化。
- Linux 设置自定义 `XDG_CONFIG_HOME` 后，两端仍共用同一数据库与锁。
- 任一启动步骤失败后，已启动服务退出、数据库关闭、锁可被下一实例取得；重复 `ZeroStart/ZeroStop` 不泄漏资源。
- RPC 断线时 Dart 停止旧播放，重连只恢复快照，不重放未确认的命令；细节见 [02-rpc](02-rpc.md)。

## 已知缺口

- `zero play` / `zero download` 等 CLI 子命令目前**不拿** `instance.lock`（zero-beat 现状）；GUI 运行期间执行它们仍可能双出声。v1 先在文档中标注，后续把锁扩展到这些命令，或在 GUI 里检测并提示。
- 桌面「关窗进小窗/隐藏」意味着 GUI 一直持有锁，TUI 无法同时运行；这是有意的互斥语义，不是 bug。
